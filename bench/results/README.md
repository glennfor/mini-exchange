# `bench/results/`

Committed benchmark output. Each subdirectory is one invocation of
`scripts/bench_all.sh` and contains:

| File | What |
|---|---|
| `machine.txt` | the machine's state at the time of the run |
| `results.csv` | one row per run, with full provenance |
| `cdf_*.csv` | percentile dumps, for the latency chart |
| `micro.json` | Google Benchmark output |
| `*.png` | charts, generated by `scripts/plot_results.py` |

**A results directory without its `machine.txt` is not a result.** The CSV
rows carry the build, git SHA, timing backend, tap state, flow mix and seed;
the machine report carries everything about the hardware that the CSV cannot.
Both are needed to know what a number means six weeks later.

Raw per-sample dumps are not committed (`bench/results/raw/` is gitignored) —
they are large, regenerable, and the percentile dump is what the charts
actually need.

## Reading a row

Look at `schedule_misses` before you look at any percentile. If it is more
than about 1% of `commands`, the run was saturated and the distribution
describes the harness, not the engine. `engine_bench` prints a warning in that
case; the CSV expects you to check.

Then check `coarse_timer`. If it is `yes`, the timing source cannot resolve
the operation being measured (41 ns per tick on Apple Silicon) and the numbers
are development-only A/B figures, not absolute percentiles.
